## 1. 최종 추천 아키텍처 (요약)

**MVP는 외부 API 조합(A안)으로 출시한다. 자체 GPU 서버는 만들지 않는다.**

```text
[브라우저]
  업로드: R2 presigned URL 직접 업로드 (서버 미경유)
  결과: Next.js 웹앱 (Vercel)
        ↓ 작업 등록
[Supabase] Auth + PostgreSQL(RLS) + pgmq 작업 큐 + pgvector 검색
        ↓ 큐 폴링
[워커] 저가 VPS 1대 (Node, Hetzner ~₩7,000/월) — GPU 없음
  ① 파일 검증·변환(ffmpeg) → ② 리턴제로 VITO STT API (전사+화자분리+타임스탬프+키워드 부스팅)
  → ③ LLM API (용어 교정·구조화 추출·회의록·확인 메시지) → ④ 임베딩 → DB 저장
        ↓
[Cloudflare R2] 원음 비공개 버킷 (이그레스 무료 → 원음 재생 비용 0)
[토스페이먼츠] 빌링키 정기결제 (개발 첫날 계약 신청)
```

- 선택 이유: 한국어 현장용어 정확도가 제품의 핵심 가치인데, 국내 특화 STT(VITO CER 5.9%)가 Whisper 자체 서버(CER ~11%)보다 **정확도에서 약 2배 우위**이고, 초기 물량에서는 비용 차이가 월 수만~수십만 원에 불과하다. 1인 운영에서 GPU·CUDA·콜드스타트 관리 부담을 제거한다.
- 예상 월 고정비: **약 ₩80,000** (Vercel Pro $20 + Supabase Pro $25 + 워커 ~$5 + 도메인·이메일 ~$5)
- 음성 1시간당 예상 변동비: **약 ₩1,300** (STT ₩1,000 + LLM ₩150 + 저장·임베딩·재시도 여유 ~₩150)
- 자체 서버 전환 검토 기준: **월 3,000 음성시간 이상** (그 전에 VITO 볼륨 티어 단가 인하가 먼저 작동)

### 2.2 판정

1. **A안으로 출시.** 이유: (a) 정확도가 곧 제품력 — 오전사된 회의록은 환불 사유다. (b) B안의 진짜 비용은 GPU비가 아니라 큐·재시도·긴 파일 분할 병합·CUDA 의존성 관리라는 엔지니어링 비용이다(1인 운영 최우선 원칙 위배). (c) 초기 100 음성시간/월 기준 비용 차이는 월 ₩10만 미만.
2. **B안은 "비용 절감 수단"이 아니라 "월 3,000시간 이상 규모에서의 마진 개선 수단"으로 보류.** 전환 전에 VITO 볼륨 티어(1,000시간 초과 시 ₩500/h, 10,000시간 초과 시 ₩400/h `[확정]`)와 클로바 B2B 협상이 먼저다.
3. **C안이 사실상의 장기 로드맵.** 처음부터 STT 호출을 어댑터 인터페이스(`TranscriptionProvider`)로 감싸 VITO→클로바→자체 서버 교체가 코드 1개 모듈 교체로 끝나게 설계한다.

## 3. AI 처리 파이프라인 설계

전체 흐름과 단계별 명세. 실패는 모두 pgmq 재시도(가시성 타임아웃 + 시도 횟수)로 복구하고, 단계별 상태를 `processing_jobs.step`에 기록한다.

```text
음성 업로드 → 파일 검증·변환 → (VAD) → 화자 구분+타임스탬프 전사 → 현장용어 보정
→ 구조화 추출 → 회의록·확인 메시지 생성 → 원문·타임스탬프 연결 → 임베딩 색인 → 사용자 수정 반영
```

| 단계 | 사용 기술(MVP) | 입력→출력 | 실패 가능성 | 재시도 | 동기/비동기 | 비용 | MVP 생략 | 출시 후 교체 |
|---|---|---|---|---|---|---|---|---|
| 1. 업로드 | R2 presigned multipart PUT (Uppy) | 파일→R2 객체 | 모바일 네트워크 끊김 | 파트 단위 재개 | 동기(브라우저) | R2 Class A 미미 | — | TUS 재개형 업로드 고도화 |
| 2. 검증·변환 | 워커에서 ffmpeg: 포맷 확인, 손상 검사, 모노 16k wav(STT용)+Opus 32k(재생용) | R2 객체→정규화 오디오 2종 | 손상 파일, 위장 확장자, 초장시간 | 1회 재시도 후 사용자 오류 반환 | 비동기 | 워커 CPU(고정비 내) | 재생용 트랜스코딩은 원본 재생으로 대체 가능 | — |
| 3. VAD | 생략(VITO 내장 처리) | — | — | — | — | — | **MVP 생략** | 자체 서버 전환 시 Silero VAD 필수 |
| 4. 전사+화자분리 | **VITO 배치 API** (diarization, wordAlignment, boostings≤1,000, domain) | 오디오→세그먼트[화자, 시작/끝ms, 텍스트, 단어TS] | API 장애, 큐 지연, 4h 초과 | 폴링 타임아웃 후 재제출(멱등키), 3회 실패 시 클로바 폴백 | 비동기(폴링/콜백) | **₩1,000/h** | — | 클로바/Azure/자체 WhisperX로 어댑터 교체 |
| 5. 현장용어 보정 | LLM 1차 패스: 전사문 + 관련 용어사전 항목(RAG 검색 상위 N) → 교정문+교정 로그 | 세그먼트→교정 세그먼트(원문 보존) | 과교정(멀쩡한 문장 변형) | diff 검증: 수치·고유명사 변경 시 플래그 | 비동기 | LLM ~₩70/h분량 | 사전 규모 작으면 단순 치환+오인식 사전으로 시작 가능 | 파인튜닝 STT로 흡수 |
| 6. 문장 정규화 | 5단계에 통합(문장 분리·문단화) | — | — | — | — | — | 별도 단계 생략 | — |
| 7. 구조화 추출 | LLM 2차 패스, **structured output(JSON Schema)**: 결정/담당자·기한/추가공사·변경/금액·일정/미확정·충돌 + 근거 세그먼트 ID | 교정문→extracted_items[] | 근거 세그먼트 누락, 환각 | 스키마 검증 실패 시 1회 재요청; 근거 ID 없는 항목은 '근거 미연결' 표시 | 비동기 | LLM ~₩60/h분량 | — | 모델 등급만 교체(스키마 유지) |
| 8. 문서 생성 | LLM 3차 패스: 회의록 + 관계자 확인 메시지(수신자 유형별) | items+교정문→generated_documents | 어조·누락 | 사용자 수정으로 흡수 | 비동기 | LLM ~₩20 | 확인 메시지 1종으로 시작 | 템플릿 다양화 |
| 9. 타임스탬프 연결 | 코드(LLM 아님): 추출 항목의 근거 세그먼트 ID→시작 ms 매핑, 재생 링크 생성 | items→원음 구간 링크 | ID 불일치 | 검증 단계에서 차단 | 비동기 | 0 | — | — |
| 10. 임베딩 색인 | text-embedding-3-small + pgvector(HNSW), 세그먼트 500토큰 청크 | 교정문→벡터 | 거의 없음 | 단순 재시도 | 비동기 | ~₩2/h분량 | 검색 자체를 2차로 미뤄도 됨(단, 차별화 기능이므로 포함 권장) | BGE-M3 자체 호스팅 |
| 11. 사용자 수정 반영 | 수정 저장→terminology_corrections 기록→회사 사전 upsert→해당 문서 재색인 | 수정→사전·색인 갱신 | 없음(동기 DB 작업) | — | 동기 | 0 | — | 공통 사전 승격 파이프라인 |

- 비용 발생 지점은 4(STT)·5·7·8(LLM)·10(임베딩)뿐이며 STT가 약 75%를 차지한다.
- 중복 실행 방지: `recordings.content_hash`(sha256)로 동일 파일 재분석 차단(런치플랜 §7 필수 통제 항목).
- LLM 선택: 추출·회의록은 **Claude Haiku 4.5**($1/$5 MTok, structured output 지원 `[확정]`) 기본, 품질 부족 시 Sonnet 5(인트로가 $2/$10 `[확정]`)로 승급, 비용 최적화 대안 Gemini 2.5 Flash-Lite($0.10/$0.40 `[확정]`). 1시간 회의(입력 ~65k tok, 출력 ~8k tok) 기준 Haiku ≈ $0.105 ≈ **₩150** — STT 대비 미미하므로 품질 우선으로 고른다.

| 1 | STT 키워드 부스팅(VITO boostings/클로바 1,000개) | **MVP 채택** | 인식 단계에서 교정하는 유일한 수단. 회사 사전 상위 빈도 용어를 요청마다 주입 |
| 2 | 전사 후 용어DB+문맥 후처리(LLM) | **MVP 채택(핵심)** | 부스팅 한도(1,000개) 초과분과 문맥 의존 용어(예: '데빠'=공종별 의미 상이) 처리 |
| 3 | 공종별 RAG | **MVP 채택(경량)** | 교정 시 전사문에서 후보 용어를 검색해 관련 사전 항목만 프롬프트에 주입(전체 사전 주입 금지 — 토큰 낭비·과교정 방지) |
| 4 | 회사별 사용자 사전 | **MVP 채택** | 수정 즉시 해당 회사에 반영(선행문서 확정 기준) |
| 5 | 오인식 사전(误→正 매핑) | **MVP 채택** | 가장 값싸고 효과 확실. LLM 이전 단계의 단순 치환 규칙으로도 동작 |
| 6 | LLM 파인튜닝 | 보류 | 데이터 부족. 수정 데이터 수천 건 축적 후 재검토 |
| 7 | 음성모델 추가 학습 | 보류 | 자체 STT 전환(B안) 시점의 과제. 축적된 '오디오+확정 전사' 쌍이 진짜 자산 |
| 8 | 발음 데이터 수집 | **수동적 수집만** | 별도 수집 활동은 하지 않되, 오인식 사전에 '들린 대로' 필드를 축적(7의 원료) |

- **재학습 금지 원칙(선행문서 §3.2 준수)**: 사용자 수정 1건 = DB upsert + 재색인 + 다음 요청부터 부스팅·RAG 우선순위 반영. 모델 학습은 검증 데이터 축적 후 별도 의사결정.

### 4.2 용어 데이터 구조 (terminology_entries)

```text
terminology_entries
  id, term_raw(원문 용어), term_standard(표준 표기), trade(공종), meaning(뜻),
  doc_expression(표준 문서 표현), synonyms[], pronunciation_variants[](발음 변형),
  misrecognitions[](자주 발생하는 오인식), usage_examples[](실제 사용 문장),
  source(출처), confidence(신뢰도 0~1), scope(common|trade|company|user),
  company_id(회사별 의미, scope=company일 때), embedding(vector)

terminology_corrections (수정 이력)
  id, entry_id, user_id, company_id, recording_id, segment_id,
  before_text, after_text, applied_scope, created_at, promoted_at(공통 승격 시각)
```

- 승격 체인(선행문서 §5): 개인 표현 → 회사 사전 즉시 → 여러 회사 반복 검증 → 운영 검수 후 공통 사전. `promoted_at`과 검증 횟수로 관리.
- 출시 전 시드: 공개 용어집·표준시방서·일본식 현장용어 순화자료를 scope=common/trade로 적재(검증문서 §3.1).

### 5.2 요구 항목별 처리

- **긴 음성 업로드/브라우저 직접 업로드**: R2 presigned multipart URL을 Next.js API가 발급, Uppy AwsS3 플러그인으로 파트 재시도. Vercel 4.5MB 한도 비관여.
- **작업 상태/실패 복구**: `processing_jobs(status, step, attempt, error, heartbeat_at)` — 클라이언트는 폴링 또는 Supabase Realtime 구독. 워커 사망 시 가시성 타임아웃으로 자동 재전달.
- **중복 실행 방지**: content_hash 유니크 + pgmq 메시지 멱등 처리 + VITO 제출 멱등키.
- **사용자별 접근 차단**: 모든 테이블 RLS + R2 키 프리픽스 `company_id/user_id/` + 서명 URL 외 접근 불가(버킷 비공개).
- **임시 서명 URL**: 재생용 GET presigned 15분 만료. 원음 URL을 DB·로그에 저장하지 않는다.
- **원음 삭제/백업**: 요금제별 보존 기간(예: 12개월) 후 R2 수명주기 삭제 또는 IA 계층($0.01/GB) 이전. DB는 Supabase 일일 백업(Pro 포함). 사용자 삭제 요청 시 R2 객체+파생 데이터 즉시 삭제.
- **로그**: 요청·작업 로그 Axiom, 오류 Sentry, 비용 이벤트는 `usage_events`에 자체 기록(관리자 비용 대시보드 원천).
- **개발 난도**: 전부 관리형 + 워커 1프로세스(~수백 줄). 1인 운영 가능 범위.

### 6.2 구독 메커니즘 설계

```text
가입 → 14일 체험 시작(카드 없이) → 체험 중 사용량 제한(총 120분)
→ 체험 만료 D-3 안내 → 카드 등록(빌링키 발급, 0원) → 만료일에 첫 승인
→ 매월 결제일 승인(자체 스케줄러 cron) → 실패 시 D+1/D+3/D+7 재시도+알림
→ 3회 실패 시 계정 '읽기 전용'(신규 분석 차단, 열람·내보내기 허용) → 해지/환불 API
```

- **토스가 제공하지 않아 직접 구현하는 것**: 결제 스케줄러(토스는 스케줄링 미제공 `[확정]`), 체험 만료 로직, 실패 재시도(더닝), 카드 만료 처리, 웹훅 멱등 처리(이벤트 ID dedupe — at-least-once 재시도 대비).
- 카드 등록 시점: **체험 시작 시 요구하지 않는다**(가입 전환율 우선). 체험 종료 시 요구. 실사용 데이터로 재검토.
- 부가세: B2C 부가세 포함 표시, B2B 카드 결제 시 세금계산서 미발행(카드 전표로 갈음 — 이중 공제 방지, 세무사 확인 필요 `[추정]`), 계좌이체 고객은 전자세금계산서 발행. 직전연도 공급가 8,000만 원 이상이면 전자발행 의무 `[확정: 국세청]`.
- **실행 순서: 개발 첫날 토스 PG 계약 신청**(선행 런치플랜 §6 확정 기준). 일반 계약(~1주) 승인 후 즉시 빌링 추가 계약 신청.

- **추천 요금제(가설)**: 베타 단일 요금제 **월 ₩49,000 / 월 10시간 포함 / 초과 시간당 ₩5,500 추가 구매 / 무제한 없음**(선행 런치플랜 §6 기준 준수). 인당 원가 ₩13,000~21,000 대비 매출총이익률 약 57~73%. 카드 수수료 3.4%+VAT 반영해도 50%+.
- **무료체험 허용량**: **총 120분** (원가 ~₩2,600/인 — 전환율 10%만 나와도 CAC로 정당화). 파일 1개당 최대 3시간, 체험 중 2파일 수준.
- **손익분기**: 유료 사용자 **3명** (49,000×3 = 147,000 > 고정 80,000 + 변동 3×13,800 + 수수료).
- **자체 서버 전환 기준**: 자체 GPU 절감액 = (블렌디드 STT 단가 − GPU ₩250)/h. 월 3,000시간에서 절감 ~월 ₩130만 vs 전환 개발 1~2개월 + 상시 운영 부담 + 정확도 하락 리스크 → **월 3,000시간(≈100명×30h 또는 300명×10h) 이상이고 파인튜닝용 자체 데이터가 축적된 시점**에 B안 전환 검토. 그 전 단계 조치: VITO 볼륨 협상·클로바 견적 경쟁.

| 사용자별 격리 | Postgres RLS 전 테이블 + R2 키 프리픽스 + 서명 URL 스코프. 교차 접근 테스트를 출시 QA 필수 항목으로(런치플랜 §10-8) |

## 9. 개발 순서 · 배포 순서

선행 런치플랜 §10의 0~10단계를 따르되, 본 문서로 확정되는 기술 실행 순서:

**개발 순서 (의존성 순)**
1. **D1: 토스페이먼츠 PG 계약 신청** + VITO 가입(무료 600분) + 도메인
2. 기술 스파이크(~3일): 실제 현장 녹음 2~3개로 VITO vs 클로바 전사·화자분리·부스팅 전후 비교, 숫자·금액·부정 표현 오류 확인, 1시간당 원가 실측 → 이 결과로 STT 최종 확정
3. 기반: Supabase(Auth/스키마/RLS) + R2 버킷/CORS + Next.js 배포 + 워커 골격(pgmq 폴링)
4. 파이프라인: 업로드→검증→VITO→LLM 교정→추출→문서 생성→타임스탬프 연결→임베딩 (§3 표 순서)
5. 결과 UI: 전사 뷰어(화자·타임스탬프·원음 재생), 추출 항목 편집, 회의록·메시지 복사, 용어 수정→사전 반영
6. 사용량·체험: usage_events, 120분 제한, 만료 처리
7. 결제: 빌링키 등록→스케줄러→웹훅(멱등)→실패 더닝→해지 (샌드박스로 선행 개발, 승인 대기와 병행)
8. 필수 페이지·QA: 런치플랜 §10-7·8 목록 그대로

**배포 순서**
1. 스테이징(테스트 키·별도 Supabase 프로젝트)에서 전체 흐름 검증 → 2. 운영 도메인·상용 키 전환 → 3. 비용 상한·알림(외부 API 월 예산, R2/Supabase 사용량 알림) 설정 → 4. 관리자 계정·복구 절차 문서화 → 5. 샘플 음성·샘플 결과 게시 → 6. 베타 사용자 모집(빌링 미승인 시 링크페이/계좌이체 병행) → 7. 빌링 승인 후 자동결제 전환

## 11. 최종 기술 결정안

**MVP 실사용 구성 (확정 제안)**

| 구성요소 | 결정 |
|---|---|
| STT | **리턴제로 VITO** (화자분리·단어 타임스탬프·키워드 부스팅 포함, ₩1,000/h) — 클로바 스피치 폴백 어댑터 |
| 용어 교정·추출·문서 | **Claude Haiku 4.5** (structured output) — 품질 미달 시 Sonnet 5 승급, 저비용 대안 Gemini 2.5 Flash-Lite |
| 임베딩·검색 | OpenAI text-embedding-3-small + pgvector(Supabase 내장) |
| 웹·DB·인증·큐 | Next.js@Vercel Pro + Supabase Pro(Auth·Postgres·RLS·pgmq) |
| 저장·재생 | Cloudflare R2 비공개 버킷 + presigned 직접 업로드 + range 재생 (이그레스 0원) |
| 워커 | Hetzner CX22 1대, Node 폴링 워커 (GPU 없음) |
| 결제 | 토스페이먼츠 빌링(D1 신청) + 승인 전 링크페이/계좌이체 |

**선택 이유**: 한국어 현장 정확도 최우선(CER 5.9% vs Whisper 11.4%) + 1인 운영 가능한 무(無)GPU 구성 + 전 구성요소가 교체 가능한 어댑터 구조 + 초기 고정비 최소화.

**예상 월 고정비**: **약 ₩80,000** (+토스 가입비 ₩220,000 1회)

**음성 1시간당 예상 변동비**: **약 ₩1,300** (월 1,000시간 초과 시 ₩850 수준으로 하락)

**자체 서버가 유리해지는 사용량**: **월 3,000 음성시간 이상** + 파인튜닝용 데이터 축적 후. 그 이전에는 VITO 볼륨 티어·클로바 협상이 우선.

**출시 후 교체 순서**
1. LLM 등급 조정(품질/비용 실측 후 Haiku↔Sonnet↔Flash-Lite) — 스키마 고정이라 무비용 교체
2. 결제 실패 더닝 고도화(필요 시 포트원 콘솔 도입)
3. 용어 자산 성장: 오인식 사전 → 회사 사전 자동 승격 파이프라인 → 공통 사전 검수 도구
4. 월 1,000시간: VITO 티어 협상 + 클로바 이중화 상시화
5. 월 3,000시간+: 전사 자체화(B안: RunPod/Modal 서버리스 + faster-whisper large-v3 + pyannote + Silero VAD, 시간당 ~₩250) — 단, 축적된 현장 오디오·확정 전사 쌍으로 **자체 파인튜닝 모델이 VITO 정확도에 근접함을 실측으로 확인한 뒤에만** 전환
6. 그 이후: 축적 데이터 기반 음성모델 파인튜닝(제품 §4.1-7) — 이 시점이 진짜 기술 해자 구축 단계
