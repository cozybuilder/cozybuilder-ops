# AI_COLLABORATION — 지시·보고·검수·승인

> 읽는 시점: AI 간 작업 전달, 완료 보고, 검수, 인수인계.
> 역할 책임: [ROLES.md](../organization/ROLES.md).

## 1. 시작 기준

- 실제로 확인 가능한 모델명만 고지한다. 세부 라우팅·fallback을 확인할 수 없으면
  `라우팅 상태 확인 불가`라고 쓴다.
- 프로젝트 사실은 현재 GitHub SSOT에서 확인한다. GitHub를 확인하지 못했으면 작업 판단을 멈춘다.
- `GLOBAL.md → PLAYBOOK.md → PROJECTS.md → 대상 AI_CONTEXT.md → STATUS.md → 관련 문서`
  순서로 읽는다. 기존 프로젝트에 `AI_CONTEXT.md`가 없으면 README와 지정된 STATUS를 사용한다.
- 확인된 사실·추정·전략 제안을 섞지 않는다.
- 현재 작업 위치가 지시서의 지정 저장소와 다르면 다른 작업을 멈추고
  `작업 폴더가 잘못되었습니다`만 보고한다.

## 2. 지시·보고 형식

지시·완료 보고·분석 보고·진행 보고·승인 요청은 하나의 복사 가능한 `text` 코드블록에 작성한다.
문서에 이미 있는 공통 규칙을 반복하지 않고 이번 작업의 목적·범위·위험·검증 기준만 명확히 쓴다.

### 새 채팅 포함 강제 규칙

- 이 형식은 기존 채팅뿐 아니라 **새 채팅·세션 재시작·컨텍스트 초기화 후에도 동일하게 적용**한다.
- 클로의 업무보고·진행보고·완료보고·차단보고·질문·승인 요청은 처음부터 끝까지 **단 하나의 `text` 코드블록 안에만** 작성한다.
- 제목·인사·요약·주의 문구·추가 설명을 코드블록 밖 평문으로 붙이지 않는다.
- 보고 도중 질문이 생겨도 코드블록을 닫지 않고 같은 블록의 `■ 질문 / 승인 요청` 구역에 쓴다.
- 새 채팅에서 이 규칙을 읽지 않았거나 누락한 것은 예외가 아니다. 진입 순서에서 이 문서를 읽고 형식을 적용한 뒤 첫 응답을 작성한다.
- 코드블록 밖 평문이 한 줄이라도 있으면 보고 형식 실패로 간주하고, 같은 내용을 올바른 단일 코드블록으로 즉시 다시 제출한다.

### 작업지시 구성 기준

작업지시서는 기본적으로 다음 여섯 구역만 사용한다.

1. 목적
2. 확정 기준
3. 수정
4. 검증
5. 문서·금지
6. 완료보고

작업지시는 가능한 한 짧게 작성한다. 작업자가 바로 실행할 수 있는 주제·방향·핵심 항목·주의사항·결과물만 남긴다.
원고 작성·조사·디자인처럼 비개발 작업은 상세 목차나 문장까지 대신 작성하지 않고, 필요한 산출물과 금지선만 전달한다.
줄 수나 분량을 맞추기 위해 필수 기준·위험·검증 항목을 생략하지 않는다.
이미 SSOT 문서와 코드에 있는 배경·공통 규칙·이전 결함 설명은 반복하지 않고 링크나 파일 경로로 넘기며,
새 결함을 막는 핵심 시나리오와 완료조건은 필요한 만큼 구체적으로 쓴다.

## 3. 완료 계약

완료는 다음 네 항목이 실제 근거로 확인될 때만 인정한다.

- STATUS 갱신 또는 불필요 사유
- commit
- push 성공 또는 구체적 보류 사유
- 검증 명령·결과·범위

보고의 PASS 문구나 commit 존재만으로 완료를 선언하지 않는다. GitHub diff·문서·테스트 근거와
대조한 뒤 `승인 / 보류 / 반려`로 판정한다.

## 4. 승인 루프

1. 코지와 코비가 현재 한 주제의 방향·범위를 정한다.
2. 코비가 지시서를 만든다.
3. 코지가 클로에게 전달한다.
4. 코지가 전달·진행 중임을 알리면 코비는 같은 지시서를 다시 만들지 않는다.
5. 완료 보고가 오면 코비가 실제 GitHub와 비교 검수한다.
6. 코지가 승인한 뒤 다음 주제를 연다.

명시적 권한 위임 계약이 없으면 현재 주제 종료 후 다음 주제로 자동 진행하지 않는다.

## 5. 검수 기준

- 실제 diff와 보고 범위 일치
- 프로젝트 금지선·승인 범위 준수
- 미해결·검증 한계 누락 여부
- STATUS·commit·push·검증 결과
- 표시 차이가 아니라 git 산출물 기준

절대 금지와 사전 승인 경계는 [GLOBAL.md §4.2](../../GLOBAL.md)가 단독 소유한다.
이 절차 문서는 그 목록을 복제하거나 완화하지 않는다.

## 6. 응답·기록 원칙

- 실제 지시와 작업에 필요한 확정 기준만 전달한다.
- 취소된 생각·검토만 한 내용·하지 않을 일·작업자에게 불필요한 대화는 지시와 보고에 넣지 않는다.
- 잠정·미확정 내용을 확정 기준처럼 기록하지 않는다.
- 먼저 스스로 조사하고, 정말 필요한 경우에만 필요한 이유를 밝힌 뒤 질문한다.
- 사용자가 요청한 답을 먼저 간결하게 말하고 다음 행동을 명확히 한다.
- 추가 주제로 넓히기 전 사용자의 의사를 확인한다.
- 출력 규칙을 추가·수정한 작업의 분석·진행·완료 보고 자체가 새 규칙을 만족해야 한다.
  실패하면 수정된 형식으로 즉시 다시 작성한다.

## 7. 반복 오류 방지 — '한 번의 실수' 원칙

문서 정합 오류 재발방지 1차(2026-07-29). 대상은 작업 결과를 바꾸는 **중요 사실**
(HEAD·버전·배포 여부·AAB/산출물 상태·데이터·계정·출시 판정 등)이다 — 단순 오탈자까지
이 절차로 확대하지 않는다.

- 최초 결함도 코지 승인 전에 즉시 수정한다.
- 최초 발생 시 근본원인과 예방 통제(재발 방지책)를 함께 정하고 기록한다.
- **같은 근본원인의 결함이 다시 나오면 단순 실수로 보지 않는다** — 절차 실패로 보고
  현재 작업 승인을 보류한다.
- 반복 원인이 기계적으로 검증 가능한 사실이면(예: Git commit SHA·Gradle 버전·산출물
  BUILD_HEAD), 자동 가드를 추가하기 전까지 그 항목을 완료로 처리하지 않는다.
- 최종 Git 사실 확인 절차는 [DOCUMENTATION_MAINTENANCE.md §1.1](DOCUMENTATION_MAINTENANCE.md)이
  단독 소유한다(여기서 복제하지 않는다).
- **신규·수정 GitHub Actions workflow는 로컬 YAML 확인·코드 리뷰만으로 완료 처리하지
  않는다** — push 후 그 commit의 실제 원격 workflow run이 PASS해야 완료한다. 실행이
  생성되지 않거나 권한·설정 문제로 확인할 수 없으면 PASS로 추정하지 않고 BLOCKED로
  보고한다. 이는 "기계적으로 검증 가능한 사실"의 한 사례다 — 외부 실행환경에서만
  검증 가능한 산출물은 그 실제 환경의 종단 증거가 완료 근거이며, 로컬 재현이나 코드
  검토로 대체하지 않는다.
