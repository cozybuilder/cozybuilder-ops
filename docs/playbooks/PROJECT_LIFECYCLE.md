# PROJECT_LIFECYCLE — 프로젝트 등록·상태·표준 진화

> 읽는 시점: 신규 프로젝트, 저장소 생성, STATUS 갱신, 공통 기준 승격.

## 1. 신규 프로젝트 등록

1. `templates/project-template/`를 복사한다.
2. 플레이스홀더를 채우고 `docs/AI_CONTEXT.md`와 `docs/STATUS.md`를 만든다.
3. `PROJECTS.md` 등록부에 프로젝트 ID·상태·브랜치·원격·STATUS 포인터 한 행만 추가한다.
4. 저장소 생성·원격 연결·첫 push를 수행한다.
5. `STATUS → commit → push → 검증` 결과를 보고한다.

프로젝트의 현재 상태나 제품 설명을 `PROJECTS.md`에 붙이지 않는다.

## 2. STATUS 갱신

`STATUS.md`는 작업일지가 아니라 현재 스냅샷이다.

- 기준 HEAD·최종 갱신일·현재 단계·현재 목표
- 진행 중 한 건
- OPEN / BLOCKED
- 최신 검증 기준
- 승인된 다음 작업 한 건
- 최근 완료 3건 이내의 근거 링크

완료 보고 전문, 전체 변경 이력, 테스트 상세, 과거 결정은 기록하지 않는다. 각각 commit,
`docs/history/`, `docs/qa/`, `docs/decisions/`가 소유한다.

코드나 제품 상태가 바뀌면 commit 전에 STATUS를 갱신한다. 갱신이 불필요한 변경이면 완료 보고에
사유를 명시한다.

## 3. 신규 저장소 부트스트랩

1. 기본 브랜치를 `main`으로 초기화한다. 기존 저장소의 확정 브랜치는 존중한다.
2. 프로젝트 템플릿을 적용한다.
3. 원격 공개 범위와 저장소 이름을 코지 승인 기준으로 확인한다.
4. `PROJECTS.md`의 포인터가 실제 파일과 일치하는지 검증한다.
5. 문서 가드를 실행한 뒤 첫 commit·push를 완료한다.

## 4. 공통 기준 승격

새 기준은 다음 순서로만 공식화한다.

1. 반복 문제나 패턴을 실제 사례에서 확인한다.
2. [DOCUMENTATION_POLICY.md](../governance/DOCUMENTATION_POLICY.md)로 정보 유형과 단독 소유 문서를 정한다.
3. 기존 기준과 중복·충돌·부작용을 검토한다.
4. 코지 승인을 받는다.
5. 소유 문서 한 곳에 반영한다.
6. 가드와 관련 검증을 실행한다.
7. commit·push 후 공식 기준으로 사용한다.

채팅 합의나 세션 기억은 commit·push 전까지 공식 기준이 아니다.
