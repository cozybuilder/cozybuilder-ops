# INC-2. QA 전용 환경까지 확대된 미승인 절대 금지선

- **발생일**: 2026-07-24
- **유입 커밋**: `d98218ac` → `94eae3`(Common Brain OS v2 문서 재편 구간)

## 사건

문서 재편 과정에서 `GLOBAL.md §4.2`의 절대 금지 목록이 다음 네 항목으로 통합됐다.

- uninstall
- 데이터 삭제·초기화
- 실기기 실데이터 수정
- QA 데이터를 실기기에 주입

이 목록은 **실사용자·운영 데이터 보호**와 **QA 전용으로 지정된 기기·계정의 승인된 초기화·
UI 자동입력**을 구분하지 않고 하나로 묶어, 승인 여부와 무관하게 전부 금지했다.

**코지의 명시적 승인 근거가 없다.** 문서 이전(재편) 작업이 새 정책 수립으로 조용히 바뀐 사례다.

## 영향

- 승인된 실기기 E2E 검수(예: CozyRent 2년 종합 실기기 E2E)와 QA 전용 기기의 UI 자동입력이
  문서상 절대 금지로 차단됐다.
- 실제로는 QA 전용 기기(Galaxy S23 SM-S911N)에서 코지 승인 하에 `pm clear`·UI 자동입력이
  필요한 검수 회차가 반복적으로 요구되는데, 문서가 그 승인 경로 자체를 봉쇄했다.
- 실사용자·운영 데이터 보호라는 원래 취지는 QA 전용 환경까지 과확대되면서 오히려
  문서의 신뢰도를 떨어뜨렸다(실제로 필요한 승인 작업마다 문서와 충돌 보고가 발생).

## 근본원인

- **문서 이전(migration)과 신규 정책 수립(policy-making)을 구분하지 않았다.** 기존 여러 문서에
  흩어져 있던 "실사용자 데이터를 함부로 건드리지 않는다"는 원칙을 `GLOBAL.md` 한 곳으로
  모으는 과정에서, 대상 범위(실사용자 vs QA 전용)를 구분하는 조건절이 요약 과정에서 빠졌다.
- 재편 담당자가 새 절대 금지선의 범위 확대를 코지에게 별도로 확인받지 않았다.
- 절대 금지선 변경에 대한 승인 요건이 `GLOBAL.md` 자체에 명시돼 있지 않아, 다음 재편에서도
  같은 방식으로 조용히 확대될 수 있는 구조였다.

## 교정

`GLOBAL.md §4.2`를 세 단으로 분리했다.

1. **절대 금지**(승인 무관) — 실사용자·운영 데이터, QA 전용으로 명시되지 않은 기기·계정만 대상.
2. **코지의 명시적 사전 승인으로 가능** — QA 전용 기기의 초기화·`pm clear`·UI 자동입력·
   테스트 전용 기준일 사용. 지시서가 대상·명령·범위·복구 필요 여부를 명시해야 효력이 있다.
3. **별도 승인 필요**(QA 환경이라도 예외 없음) — 사업 데이터 저장소 직접 주입, 공장초기화,
   계정 자체 삭제, 서버·운영 DB 변경.

`docs/operations/DEVELOPMENT_ENVIRONMENT.md §1.4`(Galaxy S23)·§5(adb 정책)도 같은 경계로
교정해 실사용 보호 기기(SM-S936N 등)와 QA 전용 기기(SM-S911N)를 문서 안에서 명확히 구분했다.

## 재발방지

- **절대 금지선이나 승인 경계를 바꾸는 모든 변경은 코지의 명시적 승인과 승인 근거를
  요구한다.** 승인 근거 없는 변경은 효력이 없다 — `GLOBAL.md §4.2`에 이 원칙을 직접 명문화했다.
- 문서 재편(이전) 작업은 **의미를 강화·확대하지 않고 소유 위치만 옮긴다**는 제약을
  `DOCUMENTATION_POLICY.md`의 무손실 이전 원칙과 함께 적용한다.
- 새 절대 금지선을 도입하는 PR·commit은 어떤 실사고·요청이 근거인지 본문에 남긴다
  (이번 사건처럼 "요약 중 조용히 확대"가 재현되지 않도록).
